A **data structure** is a way of arranging data. An **algorithm** is a set of
steps for doing something with it. Every program is some of each.

You already know several data structures — a [list](/docs/week2/lists), a
[dictionary](/docs/week2/dictionaries), a [set](/docs/week2/sets) — and you've
written algorithms without calling them that. This week names the rest and shows
how to build them yourself.

<Callout type="info">
Understand **what** a structure does before worrying about **how fast** it is.
Performance is the second question; correctness and fit are the first.
</Callout>

## The three structures in this week

| Structure | Rule | Real-world picture | Used for |
| :- | :- | :- | :- |
| [Stack](/docs/week6/stacks) | Last in, first out | a pile of plates | undo history, browser back button, expression evaluation |
| [Queue](/docs/week6/queues) | First in, first out | a checkout line | task scheduling, printer jobs, messaging |
| [Linked list](/docs/week6/linked-lists) | Each node points to the next | train cars coupled in order | playlists, anything with heavy insert/remove in the middle |

Each has its own page with a full implementation.

## Choosing a built-in

Most of the time you shouldn't build a structure — you should pick the right
built-in. This table answers the question you'll actually have:

| What you need | Reach for | Why |
| :- | :- | :- |
| Ordered items, changeable | `list` | the default; fast at the end |
| Add/remove at **both** ends | `collections.deque` | `list.pop(0)` is slow, `deque.popleft()` isn't |
| Fast "is this in here?" | `set` | near-instant, regardless of size |
| Look something up by name | `dict` | same |
| Items that must never change | `tuple` | safe to share, usable as a dict key |
| Count occurrences | `collections.Counter` | one line instead of a loop |

<Callout type="tip">
A `list` works for a stack as-is: `append()` to push, `pop()` to pop. You'll
still implement one by hand on the [Stacks](/docs/week6/stacks) page, because
understanding the structure is the point.
</Callout>

## A word on Big-O

You'll see notation like `O(n²)` on the sorting pages. It describes how the work
grows as the input grows, ignoring constants:

- **O(1)** — same cost regardless of size. Looking up `my_dict["key"]`.
- **O(n)** — cost grows in step with size. Scanning a list once.
- **O(n log n)** — the best a general-purpose sort can do. Merge sort.
- **O(n²)** — doubling the input quadruples the work. Bubble sort.

For ten items, none of this matters. For ten million, it's the difference between
a second and a week.

## Rules

1. **Choose the structure by access pattern.** LIFO → stack, FIFO → queue, lookup by key → dict, membership → set.
2. **`list.pop(0)` and `list.insert(0, x)` are O(n).** Use `collections.deque` when you need both ends.
3. **Membership testing is O(1) on sets and dicts, O(n) on lists and tuples.**
4. **Set and dict members must be hashable.** Lists and dicts cannot be keys.
5. **Big-O describes growth, not speed.** For small inputs a "worse" algorithm is often faster.
6. **Use the built-ins in real code.** Implement these structures to learn them, not to ship them.

## Common Mistakes

- Using a list for membership tests on large data, when a set is O(1).
- Calling `list.pop(0)` in a loop — that's O(n²) overall; use a `deque`.
- Optimising for Big-O on twenty items, where the constant factors dominate.
- Implementing a structure by hand in production code instead of using the built-in.
- Choosing a structure by what's familiar rather than by the access pattern.

## Practice

1. Which structure would you use for a browser's back button? For a print queue?
2. You need to check whether a username is taken, from a collection of 100,000.
   List or set — and why?
3. Time `list.pop(0)` against `deque.popleft()` on a 100,000-item collection.
